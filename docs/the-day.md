# The day: Thursday 22 October

A traditional hackathon, with Claude in everyone's hands. **Lots of building, little paperwork.** The one rule: **everyone builds**, whatever their job.

The timings are a guide. A squad can work its own way, and facilitators nudge any squad that falls behind.

## Grab and build: what that looks like

Once the first version is on screen, anything is up for grabs, and **anyone can take on anything**: a developer can do some research, a BA can fix accessibility issues, a researcher can add a new feature. Some examples:

- **Content:** rewrite the words so they're kind, plain and person-first.
- **Design:** the colours, type and layout; make it work beautifully on a phone; ask Claude for good accessible patterns and use them.
- **Research:** find out whether the main assumption holds, then change the prototype to match.
- **Data:** make the synthetic data realistic, or find open data to base it on.
- **Building:** add a screen, a filter, a map, a login, a small database behind it.
- **Quality:** try it with a keyboard and at phone width, and fix what breaks.

Say what you're grabbing out loud (or in the Teams chat), so two people don't take the same thing.

## Roles

- **Product owner:** chairs the together moments and records what the squad decides (the challenge, the idea). Makes the call on what matters next, and keeps an eye on time.
- **Merge captain:** drives the first version, keeps the shared screen on the latest version, and sorts out the order when two people need the same file.
- **Everyone, both roles included:** builds. The squad chooses who presents at show and tell.

## The shared screen

A monitor on each squad's table, run from the merge captain's laptop (`/merge-captain`). It always shows the squad's latest shared version. For the remote squad, the merge captain shares it on the Teams call.
